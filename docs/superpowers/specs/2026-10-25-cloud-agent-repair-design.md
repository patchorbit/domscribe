# Docker Cloud agent repair pilot

The exact-instance/replay foundation and SDK smoke runner are merged. The next question is whether an agent using those tools can reproduce and repair a UI bug inside Docker Cloud and return a patch whose behavior we can independently verify. The user said to continue and approved the next experiment. This is a development experiment, not a GitHub Action or a claim of developer demand.

Use two fresh in-sandbox Codex sessions with the same seeded React cart task. The cart has two lines with the same SKU and different variants; editing one quantity erroneously updates both. Give both sessions the same plain issue and full Playwright browser tools plus source access. Enable Domscribe only in the enriched condition, with MCP source/runtime/annotation tools. Keep browser, source, dependencies, prompt, model defaults, time limits and independent acceptance criteria equivalent; record differences and actual versions. One trial per condition establishes feasibility only, never statistical speed/cost superiority.

The task is a realistic seeded business defect, not an actual reported customer issue. Acceptance requires only the selected cart line to change across sorting/filtering and reload, cancellation to leave quantities unchanged, and the production build to remain functional without instrumentation. Browser localStorage is the fixture's persistence contract; there is no external backend. Before the agent, independently reproduce the exact wrong-row failure. Afterward verify the patch with held-out browser assertions; retain before/after state, screenshots, source hash, patch, agent events and usage when available. Do not treat exit zero, agent self-report or successful replay as acceptance. An empty patch, altered verifier/config/dependencies, missing reproduction, bad business state or unconfirmed cloud deletion fails qualification.

Reuse the isolated Domscribe worktree on codex/cloud-agent-repair from fresh main23063854647954f4001d05a21a928bdc12bdc6fc. Build local artifacts from a pinned public commit. Use the official SDK's codex kit and an existing OpenAI cloud secret reference; never read or create credential values, upload host auth/config, expose browser ports publicly or supply GitHub write access. Docker OAuth remains SDK-managed. Each sandbox has the smoke runner's bounded deadlines, medium compute, automatic expiration and explicit same-UID deletion. No more than one owned sandbox at a time. Missing provider authentication is a specific blocker, not permission to copy host credentials.

Implementation calls left to the builder: fixture layout, file organization, static port allocation within a fresh VM, orchestration of browser/server readiness and artifact names. Reuse existing lifecycle safeguards and add only the launch/evidence options required for this controlled workload, with regression tests; default replay behavior must remain unchanged. Pin Playwright MCP to the observed registry version and use full browser capabilities, not a custom constrained navigation harness. Keep the grader outside the agent worktree and inject/run final assertions after agent execution. This reduces accidental test tailoring; it is not a security boundary against an adversarial root process.

No automatic GitHub issue ingestion, fix PR creation, publication, production deployment or broader agent platform. Report unsuccessful trials and uncertainty honestly. The first deliverable is a repeatable pilot and actual evidence, with independent branch review and CI before PR readiness.
